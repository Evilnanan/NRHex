# 死亡之舞复用原生圣杯瓶缓回

核对当前原生regulation版本10350000与现有c0000.hks。用户指定原生8440200「使用圣杯瓶时，改为缓慢恢复」。SpEffect行的stateInfo为2015，但这不是脚本的触发身份。

## 失效原因

原生`ExecChangeFlask`（原型101）共有三处`env(1116,8440200)`精确效果ID查询，且原脚本中只有该函数引用这个效果ID。此前生成95003001复制原生参数，再由DLL周期维护，只提供了相同stateInfo，无法通过这三处判断。创建／持有该标记不代表缓回已启用。

动作首先要求7010299喝瓶通知；随后根据7010200、8440200及8970020选择原生恢复链。缓回路径发出7010230／7010231，原有其他词条分支可以额外发出7010281／7010282等效果；8970020联动中还有一处反向判断，必须同步调整，否则会额外触发本应排除的501000即时恢复。

## 最小修复

只把三处查询结果扩展为`原生8440200存在 或 死亡之舞95003000存在`，直接进入已有分支。原生效果已存在时短路，不额外查询拥有者；同时拥有两项也只执行一次原生路径。所有喝瓶守卫、其他效果条件、恢复动作和返回值保留。没有全局替换env、给其他角色赋予能力、修改原生HP公式或创建新的回血计时器。

上述动作资格只是转换的一层，不能据此删除原生stateInfo2015。当前DLL继续使用95003001保留这个原生转换状态，并且不授予／移除玩家原有8440200，避免与正常武器词条的拥有关系冲突。两秒缓扣、完整溢出损伤、原生保护／回收和气球致死通知保持不变。

## 验证

`tools/build_death_dance_flask_hks.py`从原始字节码手术修改三个查询后的分支，保存寄存器与原常量、重新定位全部跳转和调试范围，回读仅目标函数改变，精确反向恢复输入。独立DSLuaDecompiler回读确认三处拥有者判断及原恢复分支。构建脚本固定组合该补丁，不重编译反编译稿。

脚本解释夹具枚举五项效果的32种组合：不持有时与旧脚本完全一致；持有时与原生8440200已存在的原脚本在动作列表、返回值上完全相同；包括无喝瓶通知、其他词条两种联动及原生效果与拥有者同时存在。旧脚本在仅持有死亡之舞时与原生缓回路径不等价，回归可复现原错误。

这些检查证明动作分支等价、参数未改，不代表完整圣杯瓶结算等价，也不代表实际游戏每跳回血与联机已完成验收。

## 基础瞬回仍存在的现场与修正

0.17.157移除95003001是错误的简化：只接入动作资格，让原生缓回生成，并不保证普通圣杯瓶恢复同时被转换。用户先描述为死亡一次后缓回失效，随后明确修正为缓回仍在，但血瓶基础恢复也在。

只读现场确认95003000持有正常；喝瓶时先出现501000及7010299，HP由163跳至475（最大HP520，增加312恰为原生60%），之后才出现7010230／7010231，继续恢复至满。原生501000的`changeHpEstusFlaskRate=-60`，而7010230为-10。此次不是拥有者丢失或缓回动作未生成，不应重复追加缓回或只缓存一个“已复活”标志。

修复同时保留原生2015转换状态和已接好的动作分支。95003001的所有机制字段与8440200一致，只改保存、显示和网络字段；`HexBuild --death-dance-flask-check`核对该约束，并确认原生8440200、501000、7010230及7010231未被修改。状态维护仅在拥有且正常存活时缺失才申请，失去拥有／倒地时只删除私有行；原生效果清理后即使未观察到死亡帧，下一次存活更新仍立即恢复，不受墙钟刷新缓存影响。

`death_dance_flask_tests.rs`在隔离原生测试中执行真实508DF0／508E20查询，覆盖无重复添加、死亡清理再复活、未观察到清理帧、属性管理器替换和失去拥有；删除私有标记不删除原武器8440200。原生添加／移除以夹具提交节点，这项测试证明生命周期与原生状态查询，不单独证明血瓶瞬回已在游戏内消失。修复后实际基础瞬回、原生缓回、再次死亡／复活及联机仍需验收。
