# 雷电羊球：每圈动作与自转倍率同步调查

2026-11-17。用户暂不方便双人测试，本轮仅完成静态调查、原生隔离验证和诊断构建准备。没有部署、启动游戏或修改网络消息；不能把这些检查当作联机验收。

## 问题与当前实现

0.17.355 的 `ram_peer_visual` 从远端位置估计动画倍率。它是临时近似：本机 `lightning_ram` 实际用 `motion.spin.len()` 更新 `visual_speed`，再由 `roll_rate` 得到自定义倍率。空中加速、滑动和碰撞时，自转与平移并不等价。

目标是将本机使用的倍率与同一圈动作关联，接收端在应用对应动作之前获得倍率；同一圈内更新倍率不应重播该圈。尚不能宣称原生恰好每转一圈发送一个独立包：HKS 的下一圈请求、动作图状态生成和网络批次发送是不同时间点，需要实测对齐。

## 0.17.362 转速同步

队友端仅在实际播放雷电羊球滚动片段时采用发送者的自转倍率。起手、续圈、收招和受击事件均由原生快照处理。重复和迟到的转速样本不会覆盖较新的倍率或延长有效期；样本超过 0.5 秒后沿用位移估速。继续发送原有六个图变量以保留资源及诊断格式，续圈请求序号和片段进度仅供观察。

独立版与 MMV 打包均按各自输入核对全局名称表，并解包检查玩家动作图中的六个变量及类型。双人实机仍需核对队友起手的战技编号（503 为踢击、504 为雷电羊球），以及高速续滚和收招时的画面。

## 历史记录：0.17.359 实验实现（2026-11-17）

已将原生图变量方案实现于 `src/ram_sync.rs`，部署到 MMV 测试版；尚未完成双人联机验收，群友版未更新。下方较早的“尚未实施”记录描述历史研究阶段，以本节为准。

- 快照追加六项有名称、明确类型的变量：版本标记、激活代次、续圈请求序号、样本序号、实际自转倍率和 clip `localTime`。只在原生32项容量允许时追加，不覆盖原生变量，不新增私有消息号或尾部。
- 接收时先发布倍率，再让原生应用动作状态。同代同圈的新样本仅清除指定雷电羊球状态的重复触发位；下一圈仍交给原生。迟到样本只过滤对应滚动状态，其他状态、收招和中断保留。进度仅用于小幅调速，不跳帧，不重跑远端物理或伤害。
- 当前“圈号”实际来自 HKS 的续圈请求计数，尚未以双方网络样本证明与每次原生重入一一对应。大误差、丢包、加入时正在滚动仍待实测。旧资源或元数据不全时回退到原有远端视觉估算；这不代表允许双方混用不同版本的全局名称表。
- **图变量本身不足以注册全局编号。** 首次实机确认新增变量虽在图里，其全局映射全为0，名称查询失败。必须同时追加 `action/variablenameid.txt`。现按原输入末尾追加六项，保留所有旧编号、注释字节、换行与结尾填充；不能用本地图变量下标当网络编号。
- 独立版名称编号756～761，MMV当前输入767～772；运行时按名称查询并核对类型，不硬编码这些值。构建从对应版本原包生成。原版名称文件含 Shift-JIS 注释，不能强制按 UTF-8 解码重写。

MMV测试版重启后，日志确认六项类型和全局编号全部有效，运行图484个变量的最后六项映射为767～772。用户本机连续滚动的只读样本抓到真实 `a713_040010_hkx_AutoSet_00` clip 进度及逐圈回绕，松手后退出；这证明登记、节点选择和进度读取有效，**不证明已完成真实网络发送、接收或修复队友视角**。原生 clip 自身 playbackSpeed 为1也不能当成最终播放倍率，因为 Mod 在外层速度入口应用倍率。

## 静态核对结果

基于当前 `nightreign.exe`，SHA256 `9545e8732919bb6a63904cb73223641b3c4f9a67869be5722612acca413e8b3a`。以下均为 RVA。

| 环节 | 入口 | 已确认内容 |
| --- | --- | --- |
| 动作图采集 | `40A130` | 从角色动作模块写入状态快照；模块 `+8` 为角色。采集前目标缓冲尚未填充，不能读成当前状态。 |
| 状态序列化 | `DE58E0` | 将快照编码成变长记录。 |
| 状态反序列化 | `DE42E0` | 校验三类数组计数上限；逐字段读入快照。 |
| 接收状态验证 | `DE4C60` | 包含位置有效性、实体引用等检查。 |
| 应用动作图状态 | `408DB0` | 将状态、短条目及图变量交给动作图；不是施法或装备序列化。 |
| 广播动作更新 | `4EC3FA` 所在发送路径 → `DF24D0` | 原生类型 `0x46`，批量实体引用及变长快照。 |
| 接收动作更新 | `4EBEC0` → `DF1D40` | 解析 `0x46`，解码/验证后写入角色网络状态并设置更新标记。 |
| 初始完整状态 | `4E58A0` / `4EC940` | `0x37` 路径也包含动作快照，后续设计不能只考虑持续滚动。 |

快照的结构及序列化顺序：

- `+14C`：最多16个4字节状态条目，每个编码为2字节；低15位与第3字节的低位合并。原生叶函数 `D408E0`。
- `+14D`：最多4个2字节条目，从 `+140` 读取。
- `+14E`：最多32个8字节图变量，从 `+40` 读取；这些变量的具体语义尚未逐一确认。
- `+148`：4字节；`+14F`：1字节；`+150`：16字节。
- `+168`：1字节存在标记；非零时包含 `+160` 的8字节实体引用。
- `+16C`：4字节；`+170`：12字节。

单条编码长度为 `41 + 2*n1 + 2*n2 + 8*n3 + (存在引用 ? 8 : 0)`。`0x46` 外层为条目数1字节（1～64），然后每项8字节实体引用及上述变长记录。

`+170/+174/+178` 在接收调用方参与位置计算，不能借作动画倍率。采集/序列化路径未发现直接读取本 Mod 使用的动画速度 getter `3FF060`；这不等于已经证明所有图变量都不包含速率或相位信息。

反序列化函数可以留下未消费尾部，但这不能证明“给动作包追加私有尾部”在完整网络链安全：还需核对最大包长、批次边界、转发、旧客户端和联机 Mod 的处理。未采用追加尾部、占用未知字段或私有消息号的方案。

## 可选诊断模块

`ram-sync-probe` Cargo feature 默认关闭，代码位于 `src/ram_sync_probe.rs`。启用后增加四处只读前置钩子：采集、序列化、广播、应用。均保留整数参数寄存器、XMM0～5、标志、影子空间及栈参数，尾跳原函数，不猜测返回类型，不改消息内容或调用次数。

记录内容：

- `next-roll`：本机 HKS 返回下一圈请求时的事件、角色、激活代次和自定义倍率。不是已确认的网络圈号。
- `serialize`：刚采集过的角色状态，按原生字段顺序编码并记录摘要/有效字段；不会记录未初始化的填充字节。
- `send46`：发送批次中每个原生实体引用、状态摘要和长度，用于与序列化记录对应；不记录平台账号身份。
- `apply`：当前队伍拥有该海克斯的角色收到的图状态，可与发送侧有效字段对应。

角色名单由游戏更新线程读取；缓存指针只作比较键，钩子只读取当前调用提供的有效对象。名单和采集绑定均限制时效，换场清空绑定。仅在起手/滚动及结束后2秒内记录图状态，队列上限1024、总量20000条；丢记录及额度耗尽会提示。日志在更新线程排出，不在网络函数内写文件。日志仍可能影响时序，诊断结果需要在干净版本复核。

本轮仍保留原来的远端位移倍率近似，不启用新的同步协议。诊断 DLL 的版本仍为0.17.355，通过启动日志 `RamSyncProbe prepared` 及产物哈希区分；正式包不带该 feature。

## 2026-11-17 补充：变量载体与同状态重复触发

本轮是进一步研究，没有修改游戏 DLL、动作资源或网络协议，也没有启动游戏。只读现场检查时游戏已退出，因此没有新增真实联机样本。

### 原生重复事件门控

沿 `408DB0 → 4092F0 → 40AD80` 核对，`40AD80` 比较收到的状态与当前状态：状态未出现时加入事件列表；状态已出现时，仅当输入四字节条目的 `+2` 字节非零才再次加入。`4092F0` 随后通过 `D40910 → D50090 → D50300` 提交这些事件。

这个 `+2` 标志正是 `D408E0` 序列化到两字节最高位的值。因此它不是可借用的空位，而是原生“已处于相同状态仍提交事件”的控制信息。事件是否具体重启雷电羊球 clip 仍取决于动作图，不能仅凭这条分支宣称已抓到实机故障。

在独立进程执行原生 `40AE20..40AE8D` 选择循环，预先分配数组、将不可达的分配调用替换为陷阱，结果如下：

| 当前已有该状态 | 重复标志 | 加入事件列表 |
| --- | --- | --- |
| 否 | 0 / 1 | 是 |
| 是 | 0 | 否 |
| 是 | 1 | 是 |

脚本和结果在 `work/ram-animation-sync/verify-reentry.py/.json`。它验证的是原生事件选择分支，不包含动作图执行、网络发送或双人效果。不能全局清除此标志：原生连续动作本来可能需要同状态重入；也不能丢弃整个快照，因为其中还有其他图状态、变量及位置。

### 图变量的实际编码

- `D57180` 将内部32字节变量记录的 `+0` 编号和 `+8` 值打包为8字节。网络记录没有独立类型字段。
- `D57110 → D57230` 用收到的编号查询接收端动作图中的类型，再拷入32位值；`D47530` 按类型调用原生 setter，浮点型明确进入 `D567D0`。
- `D53D30/D53D60` 读取控制器 `+210` 起的32字节记录与 `+610` 计数；发送快照上限仍为32项。变量登记/排除集合与当次采集时机还需完整核实，不能认为添加图变量就会自动广播。
- `+148` 已确认是另一组图变量正值状态形成的位图：`D536E0` 逐项检查是否大于0，`D535D0` 按位还原。不是空余浮点槽，不能用来存动画倍率。
- `408DB0` 先应用状态事件，再应用图变量。如果动作进入当帧必须获得倍率，需要在原生状态应用前读取已校验的同快照字段，而不能假定原生 setter 的顺序已经满足。

只读解析原版 `c0000.hkx` 得到467个变量，类型/名称清单保存在工作目录。现有 `MoveSpeed*`、`Rolling*`、`TimeActEditor_*` 等变量有原生用途，不能因名称相近就借作 Mod 倍率。独立版与 MMV 的编号也不能假定相同。

### 当前优先方案与落地顺序

优先研究 **在各自的动作图中追加命名明确的变量，沿已有动作快照携带真实自转倍率及周期信息**，不改消息号或给批次追加未知尾部。先验证变量登记、采集、初始状态和持续更新，再决定是否实施。双方资源和 DLL 必须匹配；编号应由各自构建生成/按名称核对，不能硬编码原版索引给 MMV。

建议样本包含激活代次、圈号、真实倍率、圈内进度；若分别使用四个32位变量，原生编码增加32字节，但实际可用条目容量及批次预算必须先确认，不能挤掉原生变量。圈内进度需来自实际动画播放时间，不能以运动速度或仅累加 HKS 请求代替。

接收端先拿到与动作关联的倍率；相同圈的速度更新只更新播放速度，不重新提交起手/圈头。先保留原生必要的下一圈事件，测清同状态标志与实际循环关系。如果残余抖动确来自重复重入，再对已确认的滚动节点做圈号/进度校正，保留起手、收招、受击和死亡事件。不能为了连续视觉而把必须续播的事件一并屏蔽，也不应等待每一旧圈播放完成而积压动画。

倍率之外保留进度的原因是：只有倍率无法纠正网络晚到和圈内加速造成的进度偏差。低误差可缓慢调速追齐，大误差是否能只修改远端视觉进度需核实原生 clip 接口及 TAE 副作用；未证明前不要实现强制跳帧或独立重放。位置、碰撞与伤害继续沿已有权威路径，远端视觉修正不再执行本机物理。

相较其他路线：继续按位移估速无法解决空转/打滑；只清重复标志可能令动作播完后停住；另发私有速度包引入动作与速度错配、能力协商和传输验证成本。原生图变量路线是当前最值得先做的候选，并非已经证实完整可用的修复。

后续验收必须包含：双方同版本、低速/高速连续滚、空中自转与贴墙打滑、同圈加速、丢包/晚到、加入时正在滚、受击/死亡/离队清理，以及普通雷电羊球和其他连续战技不受影响。当前没有完成这些联机验收。
