# 雷电羊球与百般武艺：远端装备和动作选择复核

## 0.17.363 百般武艺的出招同步

本机在战技请求时读取出招手及当前武器的实际战技 ID。准备、派生和持续引导复用该次施放的记录；回到准备动作触发重铸时保留上一招的收尾，下一次出招请求才采用新结果。公开装备广播继续同步六槽装备。

原生动作快照携带四个整型图变量，分别记录手与战技、武器基础 ID、施放序号和快照序号。接收端在原生应用此快照期间按同包的出招记录解析动画，延后查询使用最近有效的记录。记录过期、武器不匹配或包内空间不足时沿用原生处理。两端需使用对应版本的 DLL、动作脚本、动作图和名称表。

隔离测试覆盖原生编解码、真实接收钩子和动作解析钩子；装备和战技参数用夹具提供。双人实机仍需核对首次起手、快速连续施放、架势派生及受击退出。

## 现场边界

基线 `9191840`（0.17.348），EXE SHA-256 `9545e8732919bb6a63904cb73223641b3c4f9a67869be5722612acca413e8b3a`。用户澄清：旧版是本人滚动、队友看到踢击；本次新增队友 getter 分支的版本尚未测试。不能记录成 0.17.348 修复失败。本轮只有静态分析与隔离执行，没有读取双方游戏进程或真实收包。

## 已确认的数据链

1. MA 的 `arts_network::update` 通过 `20BDE0 → 1F2400 → 3815B0` 导出 PlayerGameData 的六槽记录，并发送 `0x0C / 0x1F8`。序列化补丁将选定战技写入临时 `0x48` 字节记录的 `+4`，库存不变。
2. 原生 `DDAD10` 接收 `0x0C`，校验长度和内容后，以网络队伍索引取得 PlayerGameData，调用 `20DCB0 → 1F3C40 → 382E30`。`382E30 → 6C11F0 → 6C0C70` 会比较战技 ID；基础武器相同但战技不同也会重新创建实例。不是“原生只比较武器 ID，忽略战技”。
3. 以上写入的是 `PlayerGameData + 0x270`。角色构造器在 `666BD8～666BF3` 另外分配 `0x130` 字节对象，存到 `PlayerIns + 0x670`。两者不是同一份装备对象。
4. 动作类型 18 的原生解析路径是 `402830 → 402590（4027CF 分支）→ 48F6E0`，后者通过角色虚表 `+258` 取得实际手部实例，再读取战技 getter。两手共持分支走 `6A20B0`；普通持法还会用 `6A2240` 和战技参数。它使用角色的 `+670` 副本，而不是直接读取 PlayerGameData。
5. `675D20` 在 `675E77` 用 `3820F0` 从 PlayerGameData 复制装备，但并非无条件执行：`3CED90 → 4D1B20` 读取角色 `+70` 的类型表；命中对应类型、且虚表 `+130` 返回假时，从 `675D8C` 跳到 `676083`，绕过复制。当前 PlayerIns 的 `+130 → 66D630` 检查 PlayerGameData ID 是否属于 `10000～10039`。隔离执行确认类型 3/4、队伍 ID 1/2/3 会绕过；类型 0/1/2 或 ID 10000 则进入复制。尚未采到故障时队友的实际类型，不能仅凭这些编号宣称那局必然经过此分支。

这说明“0x0C 成功发送/接收、预览战技正确”不足以证明远端动作装备已更新。旧验证主要覆盖发送链和武器记录比较；没有执行远端角色实际更新分支。是否存在其他原生网络状态在故障时覆盖/刷新动作装备，本轮尚未捕获。

## 当前修复的作用和限制

0.17.348 的队友 getter 分支确实位于动作编号解析的消费路径。只要实际实例能匹配队友六槽、远端拥有标记已存在，固定的“空手→504”规则就能纠正旧踢击实例；所以它并非没有作用，也不应在未实测时回滚。

但它是雷电羊球的消费端兜底，没有修复“公开装备记录如何可靠到达动作装备”这一通用问题。百般武艺的下一招是本人随机生成的，观察者不能只凭拥有标记推导结果。`arts_actor_selection` 对远端仍假设角色实例 `+1C` 已携带发送来的战技；此次羊球分支没有改变这个前提。

百般武艺还有需要单独验证的时序：本机收招后立刻重铸并广播下一招，当前装备快照没有与某一次战技动作绑定。远端正在处理上一招时是否已经消费下一招的装备，需要结合真实动作开始/结束和收包顺序确认；这只是明确的待测条件，不能当作已经复现的网络乱序。

## 隔离验证

新增 `tools/verify_arts_animation_equipment_native.py`，在 Wine/Windows Python 的私有重定位 EXE 中执行：

- 实际 `6C0C70` 的不同战技早退比较；
- 实际 `3820F0` 装备复制主体（句柄引用计数用夹具替代）；
- 实际 `402830 → 402590 → 48F6E0 → 6A20B0` 动作编号链，包含原生左右手来源解码；参数仓库、实例引用解析由夹具提供；
- `675D20` 的上述原生守卫片段，在两个分支出口用私有返回桩停止，不执行整个角色更新。

四组动作案例通过：左右共持下，动作副本仍为503时均解析为 `712000000`；复制504后为 `713000000`。普通武器从1173改1047，对应前缀从 `773000000` 改为 `847000000`。20组装备复制守卫案例通过。新快照存在、但动作副本未更新时，解析仍使用旧战技。

报告保存在 `work/arts-peer-animation/native-validation.json`。没有执行本次 MA getter hook、真实网络传输或整个远端角色更新；这些结果证明消费关系与分支行为，不证明游戏中必现或已修复。运行命令：`python tools/verify_arts_animation_equipment_native.py`（Windows Python，`NRHEX_GAME` 指向已审查 EXE）。

## 推荐后续定位与修复方向

下一次联机采样应在观察者同一条时间线上记录：0x0C 收到的队友/六槽战技、PlayerGameData 六槽实例、PlayerIns 六槽实例与角色类型、实际动作开始时使用的手/战技/解析前缀，以及拥有标记到达时间。记录必须区分“当帧开始的这一招”和“重铸后准备的下一招”，不能只截装备菜单。

优先补齐公开装备到远端动作实例的关联：用已接收的队友身份和逻辑装备槽，核对实例代际、武器和当前动作上下文；不要按同名武器全局替换，也不要拿本机的随机表覆盖队友。若确认下一次重铸抢先影响上一招，则再处理按动作保留战技的生命周期与网络关联，不能仅靠固定延迟或反复广播。雷电羊球可以保留固定规则兜底；不建议把这种兜底直接照搬为百般武艺的随机结果推测。
