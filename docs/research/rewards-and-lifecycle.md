# 原生奖励与远征生命周期

当前七项武器倾向抽取规则见[武器倾向抽取](weapon-affinity.md)；下列0.17.16／0.17.176段落保留历史调查，角色门槛已于0.17.185被替换。

## 亮剑角色抽取限制（0.17.16）

当前EXE的`B61462`读取`[GameDataMan(3C078D0)]+8`的PlayerGameData，再读取其`C7`字节。角色初始化`200AF0`调用CharaInitParam查询及`E87DF0`角色getter后写入该字段；网络玩家构造`4D2140`同样从CharaInit的`DE`字段取得角色编号，写入PlayerGameData+C7。当前参数50000～50900的默认角色行heroId为1～10，50300／50500／50600分别为女爵4／复仇者6／隐士7；不按外观模型、法术武器或游戏画质设置判断角色。GameDataMan自身的DE字段是其他设置，不能混用。

`unavailable_hexes`同时叠加拥有、地形和角色限制，再交给运行时无放回抽取和优先快捷键替补。没有当前玩家数据或未知角色时只排除角色专属亮剑，不授予缓存的上一角色资格。潜在能力球、归属、去重和排队机制保留；当前使用一个原生模板和压缩展示记录，见[运行时奖励与扩容](reward-scaling.md)。原生getter的隔离执行、所有默认角色参数和当前读取签名经过验证；未启动游戏或联机，实际角色换人／升级奖励待测。证据在`.work/sword-balance`，成品报告`dist/sword-balance-validation.json`。

用于潜在能力、随机武器、私人掉落、按进度发放与圣杯瓶修改。下列链路已在本仓库对应的 Nightreign 版本核对；类别、模板设置和网络字段必须在目标版本重新确认，不提供固定 RVA 或自定义奖励 ID。

## 大法师开放法系海克斯（0.17.176）

`role_exclusions`读取本机真实拥有的大法师95002100，为亮出你的剑95000900、别停止咏唱95002000、回响施放95003500共用`caster_role_eligible`规则：女爵4／复仇者6／隐士7默认可抽，其余有效角色1～10在拥有大法师后可抽；未知／未准备角色不提供。拥有集合进入角色过滤前没有把大法师用作不可用标记的其他规则，因此此判断不会把角色排除当作拥有。

每次正常抽取、定向补位和逐栏刷新读取当前拥有状态；不自动发放、不重抽现存球，也不清空展示轮换。只放开三项的角色门槛，仍排除已持有项；强化死灵术、交锋等其他角色限制不变。亮剑尚未真正持有时，不提前触发亮剑对大力／不祥契约的例外。`update_chant`及`chant_pulse`移除旧的运行时角色检查：角色与大法师只决定抽取资格，实际蓄力回精只检查存活、拥有和原生有效蓄力状态，不重复判断角色或大法师。

既有角色抽取测试扩展到未知／全部字节角色编号、取得大法师前后、普通／定向／刷新、展示轮换及已持有项，验证其他过滤不被放开。统一DLL构建和原生隔离回归通过不等于完成实机玩法或联机验收；交付证明见dist/archmage-unlocks-validation.json。

## 潜在能力的完整领取链

已核对的原生路径：

```text
ItemLotParam_enemy（物品类别 7）
  → ItemTableParam（条目类别 1）
  → EquipParamGoods（goodsType=11、isEquip=0）
  → vagrantItemLotId → PermanentBuffParam
  → spEffectId → SpEffectParam
```

需要装备词条展示时另建 `AttachEffectParam`，不能以它代替奖励道具封装。只建立效果/永久能力行而缺少 Goods，可能出现未知物品名、空图标、需移入道具栏且没有获得 Buff。

从启用的原生潜在能力模板继承类型、持有、使用与不可装备设置；核对 ItemTable 的类别、启用标志、权重，以及所有引用是否存在。不要把未知字段当“跳过 Goods 封装”的开关。

原生掉落表的连续选择行可被聚合成一份潜在能力，表的基础 ID、连续槽位与调用方式共同决定内容。连续生成两项也可能合并成二选一，不能按生成 API 调用次数推断物理球数量。区分每项选择节点创建成功、整份球可见和领取后获得效果这三个结果。

抽样时先取仍可领取的池，再无放回取足够选项。池不足时的降级方案需符合设计，不应偷偷放回已领取项。下一份奖励生成要等上一份领取产生的实际拥有效果提交，避免球先消失、拥有列表还未更新时重复抽中。

## 品质与图标分别控制

当前已核对的 `RARITY` 枚举中紫色为 2、金色为 3；以目标版本 Smithbox 枚举和原生模板复核，不按颜色名称猜整数。

潜在能力球的品质沿 `ItemLotParam_enemy.lotItem_Rarity` 进入奖励描述符，选项品质还由 `EquipParamGoods.rarity` 等对应条目参与。需要两处都金色时逐层检查；换图标或染纹理不能替代品质设置。具体奖励类型的品质路径可能不同。

`lotItem_Rarity=-1`为原生不覆盖值，使用装备／物品参数的品质；不要将“跟随内容”实现成另一个固定颜色。小点心三条奖励掉落表使用此值，三选一内容和权重不变；小点心自身能力物品仍保留原品质。

## 生成带原生随机词条的武器

固定 `EquipParamWeapon` 引用与原生生成武器不是同一条掉落路径。在已核对的原生固定掉落中，类别 6 进入 `EquipParamCustomWeapon`，类别 2 则是普通武器；沿同类原生掉落复用，避免只给基础武器而丢失随机词条。

```text
ItemLot → EquipParamCustomWeapon
  → targetWeaponId → EquipParamWeapon
  → attachEffectTableId_* → AttachEffectTableParam
  → attachEffectId → AttachEffectParam → 被动 SpEffect
```

保留原生战技、武器等级、随机法术表、诅咒/禁用设置与词条槽。最高品质随机词条由对应抽取表的 `chanceWeight`、词条档位及槽位共同决定，不是把显示品质提高就自动得到最高档。检查正权重候选及原生目标武器的表，不全局改掉原版抽取池。

给具体武器时可复制其原生生成掉落，仅改确有需要的字段；相邻强化 ID、特殊攻击类别不保证唯一识别武器。手持判定见 [原生运行时](hks-and-native.md)，不要把背上装备也算当前手持。

## 私人可见与私人领取

在已分析的潜在能力生成路径中，原生函数遍历队伍玩家槽，分别抽取、建立归属描述符，再经过创建/同步。各份位置可以相同；这解释了看似一个球而各玩家独立领取的表现，不表示所有客户端互不知道对方奖励，也不表示所有奖励类型都相同。

私人奖励需同时满足显示、交互/领取、网络和移除路径：

1. 从原生会话/玩家数据确定本机槽位，保留对应归属及启用标志。
2. 仅在本线程一次自定义生成调用的范围内处理自己的管理器、掉落表和奖励类型；过滤其他玩家槽，其他原生调用原样转发。
3. 使用已经核对的本地创建分支，必要时清除该描述符的网络广播位；保留唯一 ID、位置、品质、归属和原生抽取。
4. 验证本地可见性判断也保护拾取，领取/移除会走本地清理，而非只隐藏渲染。

生成函数的多个 byte/bool 参数可能控制启用、来源检查或显式位置，不能找一个看似布尔的参数就当“私人开关”。归属 0 也可能表示不限制玩家，不能将其当本机槽位。

可以将原生可见性谓词和非网络分支复制到隔离进程，用假会话/描述符执行房主与队员槽位组合。该验证不发送包，不证明实际联机生命周期成功。还需房主/队员分别检查队友不可见、不可领取，双方在不同位置生成互不干扰，以及领取、未领取、死亡/重连后的表现。

## 达成、发放、领取分开记录

按等级/进度奖励至少区分：已达到资格、已成功发放、已领取拥有。等级会因死亡下降，最后一次观察的等级或“正在等待一个球”不能承载全部记录。

- 对已经达到的节点保存资格，即使降级、对象重建或暂时不能发球仍排队保留。
- 原生创建实际成功后才记发放。若添加领取记录立即查询不到，不能既跳过创建又把延迟出现的记录当已发放。
- 生成后到原生记录提交前，以本地预约/重入门控防重复；失败释放预约并可重试。
- 前一份未领取时暂停创建，按顺序补发后续已达成项；领取后给拥有列表一个提交机会再抽下一份。
- 快捷键测试奖励是否消费正式进度记录，应由设计明确，不能默认共用去重状态。

适用的原生保存效果可记录本局资格/发放/冷却；已核对的永久能力模板使用 `saveCategory=10`，临时行常用 `-1`。这不保证所有类别在所有游戏阶段都有相同保存行为。隐藏记录应中性、无图标/文本/视觉，仅清理自己的 ID。

新出征重置要接在已确认的原生出征初始化中：原完成标志的提前结束守卫、玩家准备/第一日开始等待共同区分新局与死亡恢复。返回圆桌可另做清理，但不能只依赖圆桌路径；重连或不同结局路径可能不同。不要以角色指针变化、等级回到低级或某个鸟交互效果单独判定新局。

进度变更可立即唤醒发放检查，未变化时低频轮询；不必通过固定数秒延迟掩盖失败。多阶段 API 用原生确认握手，避免任意等待过后就默认完成。

## 圣杯瓶容量与剩余数

容量、当前剩余瓶数和库存条目不是同一状态。赐福、夜晚结束及增加上限可能同时补满瓶子；仅观察剩余瓶数增加，不能推断增加了上限。

优先复用原生 `AddEstusCharge/RefillEstus` 等事件指令，保留原生数量上限、存储和补满行为。直接写某个库存数量未必改变真实容量。没有可靠容量 getter 时，在任务允许补满的前提下可通过原生补满、等待其提交，再读取剩余数推知容量；否则先定位容量 API，不能悄悄把探测的副作用当无影响。

当前已确认的正常第一夜结束只补满，第二夜会增加上限。容量翻倍等效果应分别处理初次获取、教堂增量、夜晚增量与夺瓶返还；返还已有容量不是新获取。不要把所有瓶数变化统一倍增。

教堂逻辑可能位于地图自身事件，某个名称类似的 common_func 不一定有调用者。检查真实构造器初始化、完成/已领取标志、模式守卫、地图实例命名空间和各变体。给已有原生领取尾部增加逻辑可保留其去重；另建监听器时需按地图本地事件 ID 范围和实际初始化方式验证。事件存在或文件已加载都不证明分支执行过。

需要“喝瓶前满血”等条件时，在原生治疗之前保存状态；治疗后的满血不是同一个条件。一次喝瓶可在相邻帧多次发出标记，适度合并需依据采样间隔，且不合并下一次合法动作。

## 地图实例、可重复战斗与监牢

监牢和野外BOSS可以放在被复用的m46地图单元中。实体、事件和完成标志沿地图实例一起重映射；新增状态、敌人、生成器和事件应留在该单元的ID范围内，通过原构造器调用传递上下文。不可用一个全局完成标志管理所有实例，也不可仅靠敌人模型判断关卡或难度。

原生监牢开门是common_func 90045000：交互9231后检查石剑钥匙8000，使用网络标志预约开启，再消耗钥匙；保留玩家槽位2／3的短延时仲裁。原开启和攻略完成标志还驱动出生过程、地图状态与赐福。需要重复战斗而不生成赐福时应另设状态，已正常完成的原生标志仍应阻止交互。

再开启至少分开“曾以自定义规则使用”“战斗占用”“本次请求”“随机选择已提交”。随机选择使用网络连接标志，并在选择提交后才放行生成事件；重载时保留已有选择，避免旧选择与重抽竞争。对不持有效果的队友，同样要保护已经切换为自定义规则的地点。

InvokeEnemyGenerator可参考原生召唤事件90045051及MSB生成器52423810，其GenType=3、LimitNum=-1、InitialSpawnCount=0，按事件重复生成。生成器的区域、部件名称和实体引用必须对应实际MSB新增内容；拷贝NPC参数时只改所需的重生字段。调用后应等待实际backread和正血量，而不是将调用完成当成生成成功。跨模型生成、死亡后再次生成、重载与多人仍需实机确认。

保留各BOSS原NpcParam中的getSoul、rewardItemLot_2及完整原生掉落链，通常比另造一套按名称估计的品质表可靠。检查掉落getItemFlagId是否会阻止第二次发奖、是否依赖组战或额外脚本。正常监牢击杀使用IncrementNetworkconnectedEventValue(8145,4,7)，common 1400对持7060001的各玩家更新9125并发放7060000；沿用该链也沿用原生七层上限。原生当前地图大空洞标记为7604，需与日历／选定地形6074区分。

EMEVD指令不能凭常见引擎版本猜编号。以NR EMEDF核对操作码、参数类型、对齐、比较类型及参数映射，并对构建后重新读取的字节解码。原地图新增项可以反向移除后重构原始MSB，验证没有改动其他模型、实体、区域和事件。

调用相同出场动画ID不保证不同敌人具备相同视觉。监牢显形在部分模型的20025 TAE中由96事件生成690031（dummy 960），193事件控制透明度。塔BOSS的90065910则先对隐藏角色的dummy 900生成690046／690047，固定等待4秒，然后请求20026、启用角色和AI；20026自身通常带透明度渐变及另一段身体特效，动作和外部黑雾是两层。原生角色特效挂点可从FLVER Dummy ReferenceID核对，不用缺少模型信息的生成区域代替角色挂点。不同模型缺少20026或有不同变体时保留分支。RotateCharacter转向请求在生成器出场方案中实测未达预期；可将朝向向量在地图局部坐标内计算后写入敌人和生成区域，两者随地图实例一起旋转。出生参照信息保存在`data/reference/world/cage-birth.json`。

事件标志ID处于地图范围内不代表有存储。当前原生EventFlagMan按1000位分组注册，已读取的传统地图及开放地图均缺6000段、包含7000段；未注册分组调用原生设置函数会静默无效。选择空闲标志时同时核对原事件冲突、实例重映射和实际分组注册，再确认设置后可读回。离线分支模拟用任意字典保存所有ID，会遗漏这种失败，需配合原生存储或实机读回验证。保留的只读类别证据见`data/reference/world/map-flag-storage.json`。

BOSS血条显示与敌人生命周期分开处理。原生90015000关闭网络同步，以20000本地玩家的距离及生死判断HUD；AI Combat=3并在传入半径内时显示，AI状态1～6均退出且玩家离开该半径、或玩家离开100米时隐藏，普通脱战等待1秒、敌人死亡等待5秒。4[9]是AI条件，3[3]是距离条件，4[0]是生死条件；比较类型4／5分别用于至少一个／至多零个角色。隐藏血条不代表敌人被击杀，不应随之释放战斗占用或结算奖励。原事件在死亡后永久结束，复制到可重复战斗时需让HUD监听器重新等待新一轮，而非直接沿用这个结束条件。不同联机玩家可独立隐藏和恢复HUD。

0.17.9针对“队友开牢正常、房主缺出场及HUD”的原生私服联机反馈，把出场播放放到独立本地事件；同步生成进度不能当作每端已播放SFX的证明。本地事件仍等待共享选择及本地backread／HP，已显形的战斗重载时不重播出场。HUD移除副本AI状态门槛，改用50米显示／100米隐藏距离，尚需联机复测其表现。另核对90015000：本地SetEventFlag(2003[66])管理5000／5001，分别预约HUD槽位0／1；不能把各自显示事件全部硬写槽位0。占槽时记住实际选择，隐藏仅清自己的预约；无空位时等待也要能被死亡、卸载、轮次结束及离开显示范围取消。离线解释能验证这些分支，不能证明私服状态同步与实际视觉时序。

模型一致不代表出场动作可以通用。检查完整TAE ID，不能仅用ID取模后存在或某类事件存在来推断用途；同一模型可能保留多个变体的动作。某个变体实测出现异常时，优先追踪它原关卡的初始化调用及参数映射，按NpcParam身份覆盖动作选择，并保留原生循环参数。例如c2500有20026和1020026，但树熔炉的原监牢初始化通过90045001绑定46700840并播放20025；这条调用比同模型的动作清单更能证明正确出场方式。

胜利结算等待与尸体移除等待分开核对。90045002在血量归零后等5秒显示胜利并增加8145，本事件没有禁用角色或移除backread；90015002的野外结算同样不直接清理角色。复制5秒等待后立即删除角色可能截断较长的死亡动画。可重复战斗若需要先开放、后清理，旧清理流程不能再写共享的新一轮状态；同一实体复用前须完成旧清理，或为并行实例提供独立实体。尸体未清理时暂时排除该实体，清理后重新入池，是不增加角色实例的一种办法；需处理重载时排除标志的复位。
