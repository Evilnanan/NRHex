# 刷怪笼复数 BOSS：原生实现调查

2026-10-10。当前游戏 EXE 1.3.3.0，SHA256 为 `9545e8732919bb6a63904cb73223641b3c4f9a67869be5722612acca413e8b3a`；原 regulation 版本 10350000，SHA256 为 `876a3ca279a4561d0c69f81fe5e510c75c59ab9a8a201694f8cf4a42c91e0268`。

结论：原生已经提供“多个独立敌人、一管群组大血条”和“多个独立敌人、多管大血条”两种流程。应把刷怪笼的抽取单位从一个角色改为一场遭遇，沿用群组血条接口；不需要在 DLL 中模拟共享生命值。

0.17.26 已把下表 13 种组合加入抽取池，共 50 种遭遇、84 个独立角色（新增 41 个战斗成员与 6 匹辅助坐骑）。完成文件回读、960 个新增事件案例和原有回归检查；尚未完成复数组战、重复奖励及联机的游戏验收。

## 生成、成员身份与通关

MSB 中每个成员保留自己的 NpcParam、NpcThinkParam、位置及生命值。`EntityGroupIDs` 把角色组织成遭遇群组。同一角色可属于两个群组，出生、血条、清理等事件可能分别引用不同群组。部分野外成员的 EntityID 为 0，仅通过名字及群组管理；复制进刷怪笼时必须分配新的独立实体 ID，不能将它们合并为一个角色。

三结晶人分别是 46600820／21／22，NpcParam 为 33501010／33500010／33502010。三份原始参数的基础 HP 都是 352，分别引用原生联机及深夜修正 7724。352 不是深夜／联机现场最终血量。组内成员没有被事件改成“其中一只代替全组承受伤害”。

原生监牢 90045001 的角色目标可以是群组。例如三结晶人传入 46605820，显形、AI 开关、动作控制因此作用于组。刷怪笼仍需对成员逐个完成可见性和模型加载确认，以免客户端漏掉尚未加载的成员。

监牢 90045002 的第 3 条指令是 4[23] `IfCharacterRatioHPValue`。三结晶人的真实绑定为：

```
IfCharacterRatioHPValue(0, 46605820, LessOrEqual, 0, Equal, 1.0)
```

即群组成员 HP≤0 的比例达到 100%，才进入胜利流程。随后保留 5 秒胜利延迟，再写通关标记及原生奖励计数。神皮双人的通关目标也是群组，虽然 HUD 分别指向两个角色。塔楼 90065911 也采用群组比例生命值和群组死亡条件。

当前刷怪笼的“一个选择对应一个复制角色、一个生成器、一个清理标记”需要扩展为“一个选择对应一组成员”。全部成员清理完后才能解除本组冷却，否则快速重开会复用仍未移除的角色。

## 大血条

指令签名按 [Nightreign EMEDF](https://soulsmods.github.io/emedf/nr-emedf.html#2003_11) 核对：2003[11] `DisplayBossHealthBar(enabled, entityId, slotNumber, nameId)`；2003[102] `LinkToBossHealthBar(enabled, healthBarNameId, entityId)`。

共用血条仍使用原生 90015000／90015021，只是目标从一个实体 ID 换成群组 ID。三结晶人的展示目标为 46605820，名称为 903350323。

本版本机器码确认这不是仅显示“组长”的血条：2003[11] 经 RVA 58d998 调用 608090；608090 识别群组目标后，通过 519030 收集组内角色，并把所有角色句柄写入该 HUD 槽位的成员列表。此处无需自定义伤害转发。此次没有继续反编译 HUD 每帧汇总公式，因此不把具体 HP 加权公式作为已核实结论。

多管血条有两条现成路线：

- 监牢神皮双人初始化两份 90015000，分别显示使徒和贵族，沿用本地 5000／5001 槽位预约。
- 塔楼 90015023 接受通关／感知群组，以及最多三对“血条实体＋名称”。按非零参数选用一管、两管或三管分支，槽位为 0／1／2。

本版本 RVA 7c48c0 明确拒绝槽号大于 2，确认该入口最多 3 管。原生多管事件还会清理 0／1／2 全部槽位并占用 5000、5001；不能直接把整段事件无条件塞入刷怪笼，以免覆盖旁边其他战斗的 HUD。应复制需要的展示分支，保留当前每位玩家的显形等待、远近隐藏及槽位占用检查。

**参数绑定必须完整。** 90015000 内 2003[102] 的未绑定字节带 `-1`，但 Parameters 会把它替换为真实名称。三结晶人的实际调用为：

```
LinkToBossHealthBar(Enabled, 903350323, 46605820)
```

RVA 58f864 从指令取出名称及实体，5f0330 遍历群组成员，6085f0 把名称写入每个 ChrIns+1A8；5f0c60／6092c0 另置 ChrIns+1FA 的标记。0.17.25 的 HealthBar 使用 `LinkToBossHealthBar(1, -1, entity)`，这与原生绑定后的名称不同。0.17.26 已对所有单体及组合血条改为真实名称；现有联机血条问题应把这项差异列为候选原因。这里只确认代码差异，没有实测它就是此前偶发缺血条的唯一原因。

## 奖励与属性

已从当前原 regulation 导出 47 种组内 NPC 的基础 HP、卢恩、掉落、群组奖励检查、联机和深夜修正引用。三结晶人、失乡骑士、石肤双王、诺克斯和监牢神皮双人的成员 `rewardItemLot_1/2` 都是 -1，不能从一个成员身上取得整个原生监牢的奖励球配置。它们的胜利群组与成员掉落需要分别处理；随后在 MSB 的 TeamFight 记录中找到了整组奖励：兽人／混种为 6400000／红化 6400010；中档组合为 6410000／6410010；神皮为 6430000／6430010。它与 NPC 的成员掉落表是两条职责不同的链。

原生塔楼组合也不符合“每个成员都放同一个奖励”的假设：

- 黑夜骑兵双人：31500020 的 rewardItemLot_2 为 6200000，31501020 为 -1。
- 龙装树守卫＋骑士：主怪为 6210000，两名骑士为 -1。
- 亚人女王＋剑圣：两名成员的 rewardItemLot_2 都是 6200000。

这些复数塔楼模板的 MSB 首／次奖励覆盖均为 -1，与目前 7 种单体塔楼模板的 6850000／6851000 武器覆盖不同。不能把当前 `TowerSources` 对首／次奖励旗标的断言直接应用到所有复数组合。接入时应逐模板核对奖励球、武器来源和红化奖励，避免漏奖励或无意重复发球。

属性继续保留成员各自的原生 NpcParam、联机修正及深夜引用；AI 使用刷怪笼独立复制的范围参数。群组成员的体型、数量、阵型与掉落职责都记录在遭遇数据中，不用一个成员的参数替代全组。

## 设计与验证范围

实现覆盖三结晶人、神皮双人与三管塔楼等下表组合，分别检验共用／双管／三管血条。遭遇数据应明确记录成员、出生偏移、群组 ID、血条模式／名称、通关成员集合和奖励来源；随机抽取一次只选一个遭遇。

本地生成事件对每个成员创建或触发生成器，保留各成员自己的生死；网络共享选择、红化决定、胜利和清理阶段，每位玩家独立等待模型和显形后展示 HUD。多管遭遇不能沿用“当前有空槽就依次显示，剩下的无限等待”的单体逻辑，需先保证本遭遇需要的槽位可用。

实现后需覆盖：任意击杀顺序、部分成员死亡后离开再返回、成员延迟加载、整组清理前连续开牢、下一天地图重载、深夜／联机成员血量，以及房主和队友分别开牢。胜利提示及监牢奖励计数只执行一次；成员卢恩和球按最终核对的原生职责处理。

证据与复查入口：`tools/HexBuild/CageGroups.cs` 的 `--cage-group-research` 和 `--cage-group-npcs`；`tools/research_cage_groups.py`。私人研究产物在 `.work/cage-groups/manifest.json`、`encounters.json`、`npcs.json`、`native-hud.c`，不打包到 dist。提取的新增 15 张 MSB 均通过当前 BHD 缓存新鲜度校验；分析时再次核对全部 347 份输入哈希，并实际替换 Parameters 后解码，未修改游戏进程内存或原始资产。


## 0.17.26 的接入与奖励消费者

实现入口为 `CageEncounters.cs`，资料为 `data/reference/world/cage-encounters.json`。抽签范围扩为 50 个相互独立的选择；保留前 37 个单体索引。每个组合分配战斗群组、各成员自己的 NPC／Think 行和生成器，出生位置在平坦环形阵型内展开，坐骑与骑手位置保持重合。原生骑乘记录重新绑定到复制角色。新增 AI 继续采用刷怪笼 30 米索敌、40／60 米返程限制；仅修改克隆行。原参数中的 HP、卢恩、联机与深夜引用、成员奖励和战斗脚本不变。

共用血条指向群组，多管指向成员，最多三管。多管组合统一预约本地 5000／5001 后显示需要的槽位；共用一管的组合只预约一个空闲槽位，取消等待不会释放别人的槽位。每位玩家独立完成成员显形；死亡的共享标记让重连者无需等待已卸载的尸体。全部战斗成员 HP≤0 后才胜利；辅助坐骑不增加通关条件，但会随整组清理。胜利计数及 8145 每组执行一次，5 秒解锁监牢、20 秒清理全部成员后解除本组冷却。延迟清理只操作旧成员，不清除新遭遇的共享状态。

原 MSB 的 TeamFight 首／次奖励、红化奖励及塔楼旗标覆盖一并读取。复数塔楼的武器覆盖位于 TeamFight.Unk14／Unk18 和 Unk1C／Unk20，而非成员 MSB 尾部；刷怪笼采用首档覆盖（两组树守卫为 6851000，双骑兵与女王组合为 6850000），保留原第二份奖励职责，红化首份也使用武器表。复制记录前校验来源哈希，回读后逐字段比较；所有引用表存在并允许重复领取。

**TeamFight.LeaderEntityID 的库名称有误导性。** 原兽人与混种分别填 46500841／46500851，神皮填 46800801，骑射手填 1028100820，这些均不是该组的实际成员。当前 EXE 的 e3a470 从 TeamFight 类型数据 +0x0C 读取此值，37f620 经 5e17f0 把它转换为地图实例旗标；37f310 检查节点 +0x24 的已领取旗标，37f760 遍历群组确认全员死亡、记录是否有红化成员，按 e3a320 的旗标覆盖或 e3a4c0／e3a4f0 的正常／红化表发球，随后设置该旗标。复制时因此把它映射到新奖励旗标，而不是映射到某个成员实体。新一轮全员生成且存活后才清除此旗标，防止旧尸体提前触发第二份球。原生容器在地图重载及反复生成中的实际表现仍列入游戏验收，静态分析不替代发球实测。

验证脚本 `tools/verify_cage_groups.py` 执行回读文件中的指令，覆盖不同首尾击杀顺序、成员加载延迟、重连时死者卸载、占满 HUD 后取消、下一场战斗开始后的旧组清理、深度 1／2 红化决定和成员标记。共 960 例；还保留单体 37 种的出生／血条检查、15984 个原红化决定及原生 getter 隔离案例、155 项 Rust 测试。额外的阶段切换、坐骑死亡与重新召唤、塔楼召唤技能、下一天重载、重复实际奖励和房主／队友分别开牢需要游戏测试。本次没有移植整张塔楼的阶段与召唤事件，也不把骑乘关系回读成功当作这些技能已经验收。

增量构建 `--cage-groups-only` 从尚未接入组战的已验证包生成暂存文件，不修改 dist；常规全量构建及刷怪笼重建会同时生成组合。安装范围为 regulation、四张监牢 MSB、四份监牢 EMEVD 和 DLL；原有其他参数表、事件、配置及手工 sword.csv 保留。
