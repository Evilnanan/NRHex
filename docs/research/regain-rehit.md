# 原生回收槽的再次受击行为

核对对象：EXE SHA-256 `9545e8732919bb6a63904cb73223641b3c4f9a67869be5722612acca413e8b3a`，2026-10-17。执行原生机器码的离线隔离测试，不代表游戏内HUD观察。

## 结论

不能把原生槽解释成每次伤害简单累加、全部额度共同获得新窗口。原生分开保存总额度（stats+168）、受保护额度（+16C）、保护剩余时间（+170）、待恢复量（+174）。

新命中重置标志成立时，426B74～426B84先清零+16C／+170／+174，保留+168；后续把新损伤乘原生回收比例加入总量及受保护量，并刷新通常4秒的窗口。4289C0每次更新时，如果总量大于受保护量，以最大HP×dt的速率削减总量，直到受保护量。窗口结束后保护量归零，剩余总量继续按相同速度衰减。

因此新命中后旧额度在该瞬间仍计入总槽，但立即失去衰减保护，很快只剩最近一次受保护的损伤；攻击足够及时仍可能在旧额度消失前回收一部分。不是瞬间完整覆盖，也不是全部叠加并续期。

## 调用点和例外

玩家43D260的43D6A9调用共享43BE60，43BF69检查正损伤并通过4B2D50／4BFCF0比较及更新原生命中身份对；新记录时43BF97设置R9B=1，经426130的426144／426175转为setter的R8B重置标志。相同记录分支可传0，不应把所有内部扣血调用都视为一笔全新受击。

原生setter同时接受回收比例、窗口倍率与窗口刷新标志；重置旧保护和刷新窗口不是同一个参数。此前隔离测试多使用reset=0，确实能观察到受保护额度累加，但不能代表普通新命中的reset=1路径。

## 复现结果

无Mod hook，HP上限1000。先受200伤害，过1秒，再受100伤害，原生比例／窗口倍率均为1：

| 时点 | 当前HP | 总可回收 | 受保护额度 |
| --- | ---: | ---: | ---: |
| 第一击后 | 800 | 200 | 200 |
| 第二击后，reset=1 | 700 | 300 | 100 |
| 再过0.1秒 | 700 | 200 | 100 |
| 再过0.1秒 | 700 | 100 | 100 |
| 此时申请回收999并结算 | 800 | 0 | 0 |

对照reset=0：第二击后总额度和保护额度均为300；过0.2秒仍为300，申请回收可恢复至1000HP。

最小探针为 `tools/probe_regain_rehit.rs`。在Windows Rust工具链下用 `rustc --edition=2021 -O tools/probe_regain_rehit.rs -o work/regain-recheck.exe` 编译，传入上述原始EXE路径运行；Linux可使用x86_64-pc-windows-gnu与Wine。探针在私有内存映射PE，执行原生426B00／4275A0／4289C0，仅以桩替代权威、角色及449状态查询，不访问运行中的游戏。原生清除／累加／衰减及回血限额代码均未修改。

## 死亡之舞的共享保护

此节记录0.17.146～0.17.159的旧优化。0.17.160按用户要求完整移除426B79 hook，原生清零／衰减恢复；不再为死亡之舞单独保留旧保护份额与时间。后续缓扣的实际损血仍按各次原生回收参数入槽。

初版0.17.146仅在426BAE拦截缓扣，原生426B79清理发生得更早，所以第二次新命中仍会使旧份额失去保护；每帧支付使用reset=0不能补回已经被清掉的旧保护。

当前实现额外在426B79安装有作用域的中途hook：只对本机存活持有者、规范stats、真实HP下降及有效449状态，跳过清零+16C／+170的单条11字节指令。426B84清零待回血+174继续原样执行。其余来源、非持有者、濒死／复活和状态拒绝均转回原指令。该拦截不直接增加额度，也不写入新计时；之后每笔实际缓扣沿原生setter累加额度及刷新窗口，停止支付后正常过期。

保留现有受保护值而不是把总槽写回保护值，可避免重保已经过期的旧额度。普通回血仍会按当前缺血量收缩总槽和保护量；不可回收伤害不增加额度、不更新窗口。当前两秒伤害队列依然逐击独立，回收保护采用原生共享窗口。

`src/death_dance_native_tests.rs`将两个正式编译的hook安装到隔离映射的当前EXE，验证真实reset=1连续受击、原生待回血取消、共享续期／自然过期、过期旧份额不复活、普通回血限幅、不可回收损伤，以及非持有者／远端／濒死／原生449拒绝的回退；由 `tools/verify_death_dance.py` 调用。不修改原生更新／排队／消费代码，不代表实机和联机验收。

## 持续扣血的无敌与锁血

用户实测报告：旧缓扣在绝招无敌过程中仍能扣至死亡，复仇者锁血也无法阻止。该反馈只覆盖这两个失败场景；后续修复尚未进行实机验收。

原因是缓扣直接使用426B00，而原生持续SpEffect结算431B30先在431BDF调用角色虚函数+210（参数0），将结果传给效果汇总函数，并非在这里统一跳过全部扣血。431C47／431C70／431E01再使用426130增减HP入口，第三参数分别为0／1／1，不能把这些分支当成同一种保护模式。426130对负变动再次检查+210，继而调用427BC0；后者在预期HP不大于0时检查属性标志、原生state143／235及行为模块+58位17，将锁血结果限制为1HP，最终才进入426B00。

玩家虚表2C307F8的+210实际为66D410，经3D3E20判断保护并检查玩家+6E4免疫计时。模式0检查行为模块+58位1、位59、角色+1F3位4及+1FB位2；模式1跳过这四类分支，但保留行为模块+58位0、句柄无效／不可用分支和玩家免疫计时。未进入碰撞函数3D3DB0／3DF380，不等于模式0不会被翻滚动作保护拦截。

0.17.150误用模式0，测试也把上述四种动作保护和两种完整免伤条件全部当成持续扣血免疫。用户随后实测复仇者翻滚期间不掉血、结束后才掉血；原生毒／腐败不受翻滚影响，大招动画无敌仍阻止持续伤害。0.17.154改为调用426130(stats,-amount,1,0,rate,window,refresh)，对齐431DF5的R8B=1设置；保留每笔原生回收参数、reset=0及43CED0结算通知。被完整免伤抵消的到期份额仍不积压、不产生回收槽，锁血只让实际失去的HP进入槽。

隔离执行真实426130、427BC0、66D410、3D3E20与模块getter路径，直接对照两种模式，增加连续动作保护下逐帧扣至0、完整免伤与动作保护重叠，以及完整免伤解除但动作保护仍在时继续扣血；五种原生最低HP机制、免伤结束无补扣及共享回收继续覆盖。新回归在旧代码首帧即失败。权威、拥有／state存在及完成通知出口仍为夹具；修复后的实际动作与联机仍需验收。

0.17.154的33组原生场景通过，自测版重启后只读确认ACTIVE=1及26处抽查钩子已安装；该加载记录不等同于翻滚／绝招动作验收。

缓扣仍按每帧dt推进累计整数份额，当前时长为两秒；只复用原生保护判断，不复制毒／腐败的motionInterval或周期跳伤时序。60Hz隔离用例逐帧核对扣血及通知次数。

## 致命伤害截断与低血量缓回

### 0.17.160 大招起手与翻滚的实际区别

0.17.159复仇者只读采样中，翻滚使用行为模块+58位1；施放绝招时从t=91.386开始出现位59，705010锁血状态到t=92.759才出现。因而只保护原生锁血状态不足以覆盖起手。早先把模式1跳过的四类标志全部视为翻滚保护是错误推断。

缓扣在位59存在时选择同一426130的模式0，由66D410／3D3E20真实原生判定拒绝；其余时间保持模式1，位1的普通翻滚仍扣血。到期免伤份额不延后、不进回收槽，也不触发结算／气球。隔离回归覆盖位59与位1重叠、连续两秒致命债务被免疫、位59解除但翻滚仍在时只扣剩余份额。现场仅采样旧版标志，修复后的实际表现需单独验收；不据此把所有游戏持续效果的参数过滤等同为该策略。

2026-10-17，运行0.17.154时只读采样复现：本机最大HP300，携带低血量为本人及附近友方缓回的原生效果7012201，参数为`motionInterval=1`、`changeHpRate=-0.5`、`changeHpPoint=-1`，现场约每秒恢复2HP。多次低血受击的独立债务仅27或12HP；27点债务支付26点时剩3HP，支付完后反而剩4HP。对应低血阶段没有观察到state143／235、stats+189的最低HP标志、行为模块+58位17或完整免伤条件。该复现不是原生锁血，而是伤害截短叠加缓回；不能据此排除其他场景真正存在原生保护。

旧capture读取setter已经限制为0的HP，用`before-after`记账，因而致命伤害最多记录受击时当前HP。原生426B00入口将原请求EDX保存在入口RSP+10，捕获点426BAE的原生栈比入口低38字节，再经hook的D0字节保存区后，从RSP+118取出原请求，作为第六个Windows x64参数交给callback；RAX保存改放独立的+C0，避免与第六参数的+28重叠。以`before.saturating_sub(requested)`记完整伤害，仍要求已通过原生资格且当前HP确实下降；不改前置免伤与最低HP规则。

隔离回归直接调用真实setter：10HP、请求-90，撤回即时扣血后记录100点债务，而非10点；支付5点、回复2点，再支付至死，只有实际失去的12HP进入原生槽。新用例在旧代码记录量断言处失败。源于现场的诊断和隔离结算通过不等于新版本已完成实机玩法／联机验收。

## 气球为何等待死亡清理

此节记录0.17.155的旧修复，已被0.17.162的实机证据更正：HP扣至0并不等于原生倒地／死亡提交，提前爆炸可以触发隐士大招吸血并循环复位。当前已移除下述`after_hp_loss`入口，改为原生状态转换；详见 `balloon-native-commit.md`。

第一次现场至少一次6999901通知与HP归零落在同一采样区间，不能断言所有死亡通知都迟到。第二次针对气球的只读复现同时读取正式0.17.154的Balloon状态：t=63.468时HP从3到0，`observed_down=1`，但`damage=0,spent=0,pending=0`；到t=70.218才变为`damage=300,spent=1,pending=0`，相差6.750秒，用户同时确认看到爆炸。延迟发生于气球请求之前，而非请求已经发出后弹体飞行了六秒。

原有触发只绑定HKS的Death／NearDeath激活、102100及3DD3D0死亡清理。原生HP增减接口426130／setter426B00只负责受保护的HP结算，不等于完整受击动作分派；死亡之舞在角色更新前执行自己的周期支付，即使随后调用HP消耗通知43CED0，也没有向气球分派本次实际致死。原有生命周期更新只标记观察到死亡，不排队，所以它可以保持HP0且未消费自爆，直到之后动作／清理入口补发通知。3DD3D0还会清理效果及行为状态，不应把该入口与HP首次归零等同。

修复在死亡之舞每笔真实扣血及原生43CED0完成后分派`after_hp_loss`，限定规范本机属性、正HP到0的变动，并复用气球原有notify／flush及去重。没有增加轮询发射，不强制进入死亡动画、不跳过救援或提前消费尚未支付的债务。隔离用例覆盖真实原生扣血与编译缓扣调用链：非致死时不爆，实际致死同步调用发射器，锁至1HP／完整免伤不爆，之后死亡标记不重复；另覆盖最大HP在拥有清理后保留、迟到复活通知及实际复活后再次触发。实际修复后的爆炸画面、敌人HP及联机仍需实测。
